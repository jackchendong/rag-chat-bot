# 异步与后台生命周期

- 先检查应用是否采用异步框架、客户端是否原生支持异步，以及实际 Python 版本。不能仅把函数改为 `async def` 就认为调用非阻塞。
- 异步函数中不直接执行阻塞网络、文件处理或 `time.sleep`；使用兼容的异步接口，必要时明确通过线程处理阻塞 I/O。CPU 密集工作按实际需求隔离，不无限创建线程。
- 顶层脚本可以用 `asyncio.run`，已有事件循环中的请求处理不能嵌套启动事件循环。
- Python 3.10 下需要超时可使用 `asyncio.wait_for` 等现有能力，不默认引用更高版本 API。
- 每个创建的后台任务明确所有者、引用、失败处理和退出路径；不使用无人管理的 `create_task` 隐藏异常或冒充持久化调度。
- 取消必须能传播，不吞掉 `CancelledError`；必要清理放在 `finally` 中，并在关闭时等待所拥有的任务结束。
- 网络调用不在同步线程锁保护区内长期等待；共享状态更新明确并发模型，避免假定单进程能保障跨进程唯一执行。
- 并行模型或任务调用有并发上限、超时和有界重试，考虑限流与调用成本。
- 流式响应明确生产者、消费者和背压策略；客户端断开时关闭所属响应流，不能让无界队列持续增长。
- 复用客户端时通过应用生命周期管理，不每次请求创建泄漏连接，也不关闭其他组件拥有的资源。
- 定时刷新、内存后台任务与持久化调度是不同能力；业务任务的认领、恢复和重复执行策略遵循项目契约。

## 容易误判的语义

- Python 3.10 中 `wait_for` 超时会取消所等待的对象并等待取消完成，因此实际耗时可能超过给定 timeout；不能把它当作严格的墙钟截止保证。
- `Task.cancel()` 是取消请求，不证明任务已经退出。关闭流程应等待任务完成；业务主动处理取消时完成清理后继续传播。
- `gather` 默认传播首个异常，但不会自动取消其他子任务。需要失败即停止时显式管理剩余任务的取消与等待；`return_exceptions=True` 的结果逐项检查，不能全部视为成功。
- `to_thread` 或执行器中的线程不会因为等待它的协程被取消就自动停止。阻塞操作仍需自身超时，涉及副作用时不能直接盲目重试。
- Semaphore 限制同时执行量，不限制预先创建的任务总数。大量任务应使用有界队列或分批提交，避免一次创建全部任务。
- asyncio 的锁和队列面向事件循环内协作，不当作线程间或进程间同步工具。取消后剩余线程访问共享资源的行为也需明确。
- `shield` 仅在操作确实应独立于调用方取消时使用，保留内部任务引用并管理最终结果，不能用它普遍阻止服务退出。
- 超时预算尽量覆盖整个操作及重试，退避等待也支持取消；测量经过时间使用单调时钟，不受系统时间调整影响。

## 验证与参考

验证取消、超时、任务异常和服务关闭行为。有现成测试体系时用明确事件与有界等待验证，不依赖随机 sleep 推测调度顺序。仅以“请求已取消”不能推断外部模型调用或数据写入从未发生。

需要核对具体 API 时查阅 [Python 3.10 asyncio 任务文档](https://docs.python.org/3.10/library/asyncio-task.html)，以目标版本为准，不套用新版 TaskGroup 行为。
