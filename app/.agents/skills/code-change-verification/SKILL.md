# 改动验证

## 分类与执行

1. 用原始需求、Git 状态及新文件内容确定任务范围，不漏掉未跟踪文件。
2. 查看实际解释器、依赖清单和检查配置，命令遵循 [Python 工具链](../python-tooling/SKILL.md)，不执行不存在的 `make` 或 uv 工作流。
3. 迭代时先做聚焦检查；实现稳定并完成适用审查后，再做项目已有的格式、lint、类型和测试检查。没有配置的检查明确不适用，不虚构通过。
4. 有格式化步骤时先执行，因为它会改变交付内容；后续检查依据最终文件执行。工具仅检查相关路径，不重写全项目。
5. 顺序执行适用检查，失败后先区分本次问题、既有问题与环境限制；修复后重跑被改动影响的检查，不静默跳过。
6. 依赖输入未变且环境已就绪时不重复安装。外部服务集成测试与纯本地检查分开，不能自动使用真实模型密钥。

## 技能结构检查

本地脚本只检查仓库技能的受限元数据格式、名称、文件引用、占位符和空白，不是完整 YAML 解析器，也不能证明技能行为正确。

从 `app/` 在 Git Bash 执行：

```bash
./.venv/Scripts/python.exe .agents/skills/code-change-verification/scripts/validate_skills.py
```

PowerShell 使用同一路径并以 `&` 调用解释器。脚本不安装依赖、不修改文件、不调用网络，默认验证 `app/.agents/skills/`，可用 `--root` 指定另一技能根目录。

标准 skill-creator 校验器已可用时也可执行；缺少其依赖时如实报告，不把本地结构检查称为标准校验器通过。

## 指令行为抽查

技能规则变更额外检查真实场景：纯文档不安装应用依赖；缺少后端框架不编造启动命令；付费探测先确认范围；已有用户改动不被覆盖；Python 3.10 不误用新版 API。独立行为评估只在确有价值且可用时开展，不为简单技能维护设置强制多轮门槛。

最终说明每项检查的实际结果和未验证部分，语法检查、mock 测试、真实联调是不同证据。
