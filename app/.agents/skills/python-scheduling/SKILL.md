# 定时任务与执行一致性

## 时间规则

- 分开表示一次性时刻、周期规则和运行记录。持久化业务时刻用带时区的时间或明确 UTC 表示，周期规则保留 IANA 时区，不仅存储当前 UTC 偏移。
- 日历计划使用墙钟时间，经过时间与本次执行超时使用单调时钟；单调时钟值不能存储为跨进程重启的执行时刻。
- 对夏令时造成的不存在时间或重复时间定义明确策略，不能只给本地 datetime 附上 tzinfo 就认为时间有效；重复时间的 `fold` 选择也应与业务规则一致。
- Windows 可能缺少 IANA 时区数据库；检查部署环境，在需要时通过既有依赖方式提供 tzdata，不悄悄回退为服务器本地时区。
- 周期计划明确从计划时刻还是完成时刻计算下一次执行，并确定错过执行时的跳过、合并或补执行策略，补执行数量有界。

## 保存与认领

- 创建成功只能在持久化确认之后返回。用户重复提交和结果未知的重试需要明确的幂等标识及作用范围，不能靠前端按钮禁用保障。
- 有多个执行者时，在存储能力范围内通过原子更新、事务或等价认领机制判断任务可执行，不能用“先查再写”避免重复认领。
- 认领区分任务标识、一次执行标识与当前所有者。涉及超时接管时用版本或所有权条件防止旧执行者覆盖新状态，不仅依赖本机锁。
- 外部模型调用前后分别处理持久化失败窗口；不要持有数据库事务或全局锁等待漫长网络响应。
- 不预设数据库或 Redis 存在，也不宣称本地进程内实现能提供跨进程一致性。

## 执行与恢复

- 调度器扫描或唤醒只负责安排执行，执行器负责受控任务类型、并发和结果记录；启动与关闭遵循应用生命周期。
- 每次运行有可追踪记录、开始结束时间、尝试次数和安全的失败信息；大量输出设上限，不将完整秘密或敏感提示落入日志。
- 重试只针对明确可重试情形，次数、总预算与退避有界，避免多个失败任务同时形成请求洪峰。
- 超时或断连不证明外部副作用未发生。明确系统是允许至少一次重试、宁可漏执行，还是具备实际幂等保障，不声称天然恰好一次。
- 重启恢复对处理中任务确定保留、超时接管或人工处理策略；失去认领权的执行者不能再写入成功结果或继续声称拥有任务。
- 关闭时停止新增认领，按政策等待或取消正在执行的任务，并保留可恢复状态；不把进程退出当作任务成功。

## 验证

有测试体系时，用可控时钟与隔离存储覆盖时间边界、多个执行者竞争、认领后崩溃、旧执行者迟到写入和响应丢失后的重复提交。fake 验证决策；原子认领及事务语义用对应真实存储的隔离集成测试验证。

时间基础查阅 [Python 3.10 zoneinfo 文档](https://docs.python.org/3.10/library/zoneinfo.html)；不要把时区转换支持等同于完整的调度策略。
