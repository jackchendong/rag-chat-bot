# 敏感日志审查

## 追踪真实数据流

- 从受影响代码查找 logging、print、warnings、异常格式化和遥测输出，检查别名、封装、回调及自定义 handler。
- 搜索只提供候选，不证明安全或完整。追踪值的生产者、异常链、URL、格式化参数及 `extra` 字段，明确是否含模型、用户、任务或密钥数据。
- 区分诊断输出和明确面向用户的任务结果；后者仍需满足权限与数据归属，不能因属于结果就无条件公开。
- 查看 [脱敏验证清单](references/redaction-validation.md)，只采用实际项目支持的策略，不编造官方 SDK 的日志开关。

## 修复边界

- 优先在共享边界修复已证实泄露，保留必要的请求/任务标识、错误类别和耗时，不记录完整提示、响应或授权头。
- 敏感模式下在格式化和读取敏感对象之前做决策。仅把渲染文字替换为星号不够，原对象不能留在日志参数、extra 或异常信息中。
- 对未知异常使用固定安全诊断或已验证的脱敏分类；`logger.exception`、`exc_info=True` 可能通过异常链再次暴露内容。
- 外部 URL 中的用户信息、查询参数和片段可能含秘密；不要只去掉授权头就认为路径和名称安全。
- 日志处理不得改变原本的取消、清理、重试或结果返回；不通过吞掉业务错误实现“无泄露”。

## 证明与报告

有测试体系时在实际调用边界验证完整 LogRecord 和最终格式化输出，使用不含真实密钥的唯一哨兵值。报告确认问题、修复、保留的必要输出和尚未完成追踪的路径，不把零搜索结果或日志快照称为完整安全证明。
